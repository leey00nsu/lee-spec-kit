# Decisions Log

기술 결정과 그 이유를 기록합니다.
canonical docs surface 밖의 unmanaged docs 산출물(예: `docs/plans/*`, `docs/superpowers/*`)이 있더라도, 실제로 채택한 대안과 선택 이유는 이 파일에 다시 남겨 Feature의 결정 이력을 유지합니다.

> ADR(Architecture Decision Record)은 구현 중 내린 중요한 기술/구조 결정을 남기는 기록입니다.
> 나중에 "왜 이렇게 만들었는지"를 추적하고, 팀 합의를 재확인하기 위해 작성합니다.

> 형식: `DNNN: {결정 제목} ({YYYY-MM-DD})`
> 결정 ID는 Feature별로 독립된 번호를 사용하며 Feature ID와 관계없이 `D001`부터 시작합니다.

기록 원칙:

- 새 ADR 생성에는 `npx lee-spec-kit decision add <feature-ref> --title "..." --context "..." --decision "..." --rationale "..." --evidence "..."` 사용을 우선하세요.
- 수동 작성도 마지막 ADR 뒤에 추가해 D001 → D002 순서를 유지하세요. 문서 안내문 앞에 삽입하거나 기존 ID를 재번호화하지 마세요. 같은 결정의 재실행·검증 결과는 해당 ADR의 Trace/Evidence를 갱신하고, 새 선택이나 범위 변경일 때만 새 ADR을 만드세요.
- 모든 ADR은 **Decision(무엇을 선택했는가)** + **Trace(어떻게 고민했고 무엇을 확인했는가)** 를 함께 남깁니다.
- 작성 타이밍을 고정합니다.
  - 태스크 시작(`[TODO] -> [DOING]`): `Context/Constraints`와 `Trace(초기 가설)`를 1~3줄로 먼저 기록
  - 태스크 완료 직전(`[DOING] -> [DONE]`): `Options/Decision/Rationale`를 최종화하고 `Trace`를 보강
  - PR 머지 후: 실제 결과/영향을 `Trace(머지 후 확인)`에 1~2줄 추가
- 모든 ADR에는 최소 1개 이상의 **Evidence 링크**(커밋/PR/테스트 로그 중 하나 이상)를 남깁니다.
- 디자인 시스템 변경이나 예외를 기록할 때는 영향 받는 규칙과 범위, 예외 이유, 제거 조건, 실행 가능한 정본의 동기화 영향을 함께 남깁니다.

## 성능 개선 근거 기록

성능 개선이 목적이거나 결과에서 성능 향상을 주장하는 변경에는 해당 ADR 안에 `### Performance Evidence`를 작성합니다. 일반 변경에 빈 성능 표를 추가하지 않습니다. 아래 형식을 필요한 ADR에 복사하고 실제 측정값으로 채웁니다. 같은 결정의 재측정은 날짜·조건·원본 근거를 보존하며 해당 ADR에 추가합니다. 최초 As-Is와 과거 결과를 최신 수치로 덮어쓰지 않습니다.

1. **구현 전**: Spec의 성능 요구사항과 연결할 지표·단위·개선 방향·목표·허용할 부작용을 정하고 Plan의 Verification Contract에 측정 절차를 기록합니다. 승인된 범위에서 변경 전 기준선을 먼저 측정합니다. 기존 실행 환경에서 실행할 수 없으면 그 이유와 확보 가능한 이전 로그의 출처를 기록합니다. 구현 후의 값으로 과거 기준선을 추정하지 않습니다.
2. **측정 조건**: 전후 각각의 측정 일시·시간대, 코드 commit SHA와 미커밋 diff 식별자(해당 시), 벤치마크 도구·스크립트 버전, 재현 명령·작업 디렉터리·비밀정보를 제외한 설정을 남깁니다. 하드웨어·CPU/메모리·OS·런타임·의존성·배포 설정, 데이터셋의 식별자·크기·seed, 요청 패턴·동시성·부하·측정 시간, 캐시 cold/warm·워밍업·반복 횟수·표본 수·집계 방식을 기록합니다. 성능에 영향을 줄 수 있는 조건 차이는 명시합니다.
3. **구현 후**: 같은 시나리오·지표 정의·환경·부하·도구로 재측정합니다. 시나리오나 cold/warm 결과를 섞지 않고 행 또는 표를 나눕니다. 지표에 맞게 median/p95/p99·최솟값/최댓값·표준편차·신뢰구간 등 실제로 계산한 분포·편차를 함께 남기고 표본 수를 명시합니다. 측정하지 않은 통계값을 만들지 않습니다. 속도 외에 오류율·정확성·CPU·최대 메모리·비용 등 관련 부작용도 확인합니다.
4. **계산과 판정**: 절대 변화량은 `After - Before`, 상대 변화율은 `(After - Before) / Before × 100`으로 기록합니다. 값이 낮을수록 좋은 지표의 개선율은 `(Before - After) / Before × 100`, 높을수록 좋은 지표는 `(After - Before) / Before × 100`이며, 개선율 양수는 개선·음수는 회귀입니다. 0 또는 누락된 기준선의 상대값은 `N/A`와 이유를 적습니다. 퍼센트 지표는 `%` 상대 변화와 `pp` 차이를 구분합니다. 잡음 범위의 차이, 비교 불가능한 조건, 회귀·목표 미달을 그대로 설명하고 모든 변화를 해당 코드 변경의 효과로 단정하지 않습니다.
5. **근거와 전달**: 재현에 필요한 비밀정보 없는 원본 로그·실행별 수치·프로파일·사용한 임시 스크립트/설정은 실제 활성 Feature의 `artifacts/performance/`에 필요한 만큼 보존하고 ADR에서 상대경로로 연결합니다. 기존 프로젝트 벤치마크 코드에는 경로와 revision을 연결하며 새 영구 벤치마크·테스트는 승인된 Verification Contract 범위에서만 추가합니다. `artifacts/change-report.html`에는 같은 수치와 ADR 링크를 요약하고 목표·실측·미측정을 구분합니다. 주 에이전트가 ADR과 보조 산출물을 저장하며 worker는 기존 쓰기 계약 안에서 측정하고 명령·조건·결과·근거 파일 위치를 전달합니다.

추후 추세 비교에는 `api.search.latency.p95`처럼 Feature ID와 무관한 안정적인 지표 키와 시나리오·통계 정의를 사용합니다. 정의·환경·데이터가 달라지면 같은 시계열처럼 합치지 않고 구분합니다. 여러 변경의 개선율을 단순 합산하지 않습니다. `decision add`는 기본 ADR을 만들므로 생성 후 해당 ADR에 아래 성능 항목을 보완합니다.

**가상 계산 예시 — 이 저장소의 실측이 아닙니다:** p95 지연 420 → 250 ms는 절대 변화 -170 ms, 상대 변화율 -40.48%, 개선율 +40.48%입니다. 처리량 120 → 180 req/s는 +60 req/s와 개선율 +50%이며, 동시에 최대 메모리 220 → 250 MiB라면 메모리 회귀 +30 MiB도 기록합니다.

다음 예시의 값은 형식 안내입니다. 실행 증거가 없는 `미측정`이나 `비교 불가`를 완료된 개선으로 표현하지 않습니다. 측정 불가 이유·누락 조건·해결 방법과 실제 후속 작업(필요 시)을 기록합니다. 배포 후 측정이 필요한 경우 개발 환경 수치와 분리하고, 실제 운영 검증 전에는 운영 개선이 확인됐다고 쓰지 않습니다. 이 지침은 기록·리뷰 기준이며 새 자동 벤치마크 실행기나 workflow 승인 게이트를 추가하지 않습니다.

```markdown
### Performance Evidence

- **Requirement / Scenario**: {성능 요구사항·사용자 시나리오·측정 경계}
- **Goal / Guardrails**: {목표와 허용 가능한 오류율·정확성·자원·비용 조건}
- **Status**: {측정 완료 / 미측정 / 비교 불가와 이유}
- **Before Run**: {일시·시간대, 코드 SHA/diff, 도구·스크립트 revision}
- **After Run**: {일시·시간대, 코드 SHA/diff, 도구·스크립트 revision}
- **Environment / Workload**: {전후 환경·데이터·부하·캐시 조건 및 차이}
- **Reproduce**: {cwd, 전후 실행 명령, 비밀정보 없는 설정}
- **Sampling / Statistics**: {워밍업·반복·표본 수·집계·편차·제외한 실행과 이유}

| 지표 / 시나리오 / 통계 | 단위 | 개선 방향 | Before (실측) | After (실측) | 절대 변화 | 상대 변화율 (%) | 개선율 (%) | 목표 / 판정 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| {지표} | {단위} | {낮을수록 / 높을수록} | {값} | {값} | {After-Before} | {값 또는 N/A} | {값 또는 N/A} | {목표 달성·회귀·불확실} |

- **Side Effects / Limitations**: {오류율·정확성·자원·비용·측정 잡음·조건 차이·인과 해석 한계}
- **Evidence**: [Before 원본](artifacts/performance/before.json), [After 원본](artifacts/performance/after.json) — 실제 보존 파일에 맞게 변경
- **Conclusion / Follow-up**: {확인된 효과·미확인 범위·필요한 후속 검증}
```

## Spec 결정 확인

질문은 첫 ADR 추가 시에도 보존되도록 D001 ADR 섹션 앞에 기록합니다. 실제 `## SC-01: 제목`(`###`도 허용)을 사용하고 D001 번호와 독립적으로 SC-02부터 이어갑니다. 아래 fenced 예시는 안내일 뿐 seed의 실제 OPEN 질문이 아닙니다. 실제 질문이 있을 때만 fence 밖으로 복사합니다. 두 언어 모두 필드명과 상태 값은 영문 그대로 유지합니다.

Status 값은 OPEN | RESOLVED | DELEGATED | DEFERRED입니다. OPEN은 Spec 결정 확인 완료를 막습니다. 모든 종결 기록의 Answer, Decision, Spec Refs에는 자리표시자가 아닌 구체적인 내용이 필요합니다. RESOLVED는 실제 사용자 답변과 그에 따른 결정을 기록합니다. DELEGATED는 사용자의 명시적 위임과 에이전트가 내린 선택·적용 범위를 기록합니다. DEFERRED는 사용자의 명시적 보류 합의, 제외 범위와 구체적인 후속 조치를 기록하고 Spec Refs로 해당 범위·인수 조건을 연결합니다. 침묵·기본값·시간 초과·리뷰 maxRounds 소진을 동의로 간주하지 않습니다.

질문 전에 사실을 조사하고 기존 답변을 재사용합니다. 제품·범위·인수 조건·호환성에 관한 독립적인 선택을 한 번에 clarificationPolicy.maxQuestionsPerRound개까지(설정 workflow.specClarification.maxQuestionsPerRound, 기본 3) 선택지·권고안·장단점과 함께 질문하고 필요한 답변을 기다린 뒤 종속 질문을 이어갑니다. 일상적인 구현 세부사항은 묻지 않습니다. 답변과 Spec 범위·인수 조건은 같은 턴에 반영합니다. 새 범위·동작의 중대한 변경은 관련 선택을 다시 열고 이전 답변을 이력으로 보존하며 Spec의 Clarification Status를 Pending으로 되돌립니다. 모든 기록이 유효한 종결 상태이고, 질문이 불필요한 이유나 결정 반영 내용을 실질적으로 설명하는 Spec의 Clarification Summary가 있을 때만 Complete로 바꿉니다.

```markdown
## SC-01: {제품 또는 범위 선택}

- **Status**: OPEN
- **Question**: {사용자 입력이 필요한 선택}
- **Options**: {대안과 각 장단점}
- **Recommendation**: {권고안과 이유}
- **Answer**: -
- **Decision**: -
- **Spec Refs**: -
```

## D001: {결정 제목} ({YYYY-MM-DD})

- **Context**: 문제 상황 또는 배경
- **Constraints**: 제약 조건 (시간/기술/운영/호환성)
- **Options**: 고려한 대안들
- **Decision**: 최종 선택
- **Rationale**: 선택 이유
- **Trace**:
  - **DOING 시작 시점**: 초기 판단/가설
  - **DONE 전 확정 시점**: 선택 근거 최종화
  - **머지 후 확인**: 실제 결과/영향
- **Evidence**:
  - **Commit**: 커밋 해시 또는 링크
  - **PR**: PR 링크
  - **Test/Log**: 테스트 결과/로그/스크린샷 경로
- **Consequences**: 결과 및 영향 (선택사항)
