# Standalone documentation integration

`workflow.docsCompletionStrategy` is a new optional setting. Its default is `inherit`, including when the field is absent in older configurations. In local mode, the effective docs strategy follows `workflow.completionStrategy`: `local-ff` or `local-squash`. An explicit docs override can select either of those strategies in a standalone local project with managed code integration. Embedded docs already integrate with code and cannot use a separate override. GitHub mode retains its existing docs ff path; it supports `inherit` or `local-ff`, and rejects an explicit `local-squash` override. Code strategy `none` does not authorize managed standalone docs integration. Configuration inspection reports these unsupported overrides instead of silently changing their meaning.

Use `init --docs-completion-strategy <strategy>` or `config --docs-completion-strategy <strategy>` to configure the field. `update` adds `inherit` when missing and preserves explicit overrides. `detect --json`, `workflow-stage --json`, and workspace JSON report the effective `docsCompletionStrategy` for standalone projects.

Keep task commits on the Feature worktree throughout execution. Each task still needs its docs and project checkpoint, strict task gate, declared checks, and workflow sync audit. Completion follows code verification and approved code integration, docs integration verification, docs cleanup, project cleanup, then `done`. Implementation approval and local merge approval remain distinct.

`workspace sync-docs` merges the current docs base into the Feature docs worktree. It may create a merge commit there. Resolve conflicts and rerun validation before continuing. `workflow-stage` returns `workspace_sync_docs` when synchronization is needed. Shared-document conflicts remain in the Feature worktree; neither the base nor another Feature is rewritten.

`workspace merge-docs` requires clean source and base worktrees, the expected branches, verified code integration, and a source that contains the latest docs base. Allowed paths are the selected Feature's canonical SDD, metadata and `artifacts/`, plus approved Curated Documentation Impact docs targets linked from task `Docs` lists. The net diff is measured from the latest synchronized base to source, so changes originating from other Features on base are preserved and are not attributed to this Feature.

For `local-squash`, the CLI creates one canonical Feature-scoped commit with the latest docs base as its sole parent and the verified source tree as its tree. Its body contains the integration receipt. Source task commits and sync merges do not become ancestors of the resulting base commit. For `local-ff`, the compatibility path appends an empty receipt commit to the source and advances base by fast-forward. Both paths verify the integrated tree and preserve source evidence. Integration retries reuse a valid receipt rather than adding another commit.

The v2 receipt records the original docs base, synchronized base, verified source tip/tree, source task checkpoint, effective docs strategy, approved paths, task gate policy, evidence refs, and verified code integration/checks. The enclosing commit supplies the integrated commit ID; the receipt supplies its tree. Runtime state caches this evidence and can be reconstructed from Git. Legacy empty ff receipt commits remain readable after policy upgrades; no previous integration is automatically rewritten.

Squash source evidence lives under `refs/lee-spec-kit/docs-integrations/`. An immutable lightweight tag under `refs/tags/lee-spec-kit/docs-evidence/` preserves the same original tip for transport by ordinary clones. A local clone receives the tag and reconstructs the internal ref. When explicitly publishing docs remotely, publish the exact `portableEvidenceRef` returned by the CLI together with the base; pushing only base does not publish unreachable source history. A `--no-tags` clone or a remote lacking the evidence tag needs that exact tag restored before completion can be verified. Stage inspection performs no remote fetch or push. Preserve evidence refs/tags after cleanup; they intentionally retain the original checkpoints even though the base graph is linear.

Cleanup validates the receipt, commit parent/tree, exact source tip/tree, approved scope, task checkpoint, evidence and code verification before removing the selected worktree and branch. Squash cleanup uses that proof instead of requiring source ancestry. Missing or changed evidence, changed source, changed checks/strategy, dirty worktrees or invalid receipts stop cleanup and preserve data. The strict task gate reads the preserved checkpoints only when the live task document still matches the verified receipt; a later task edit must pass the live gate. Multiple DONE transitions in an executing task commit remain blocked.

Base advancement requires sync and revalidation. Conflicts require resolution in the existing source worktree. Invalid receipts or missing evidence require restoring the recorded evidence and policy before retrying; never bypass cleanup checks by deleting a branch manually. Completed integrations remain valid across unrelated later base commits. Old history cleanup, rebase and force-push require a separate explicit request with backup and verification.
